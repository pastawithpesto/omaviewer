# Keyboard and pointer controls plan

Status: implementation added; see README and phone-test.md for verified behavior and remaining limits.

## Current behavior and concrete changes

| Area | Present behavior in the app | Required change |
| --- | --- | --- |
| Direct touch | **Click** taps and drags; **Scroll** swipes send wheel events; **Pan** moves the local viewport; pinch zoom is local | Keep these working modes, explain their gestures beside the selected mode, and add **Trackpad** |
| Right-click | **More → Right-click next tap** already sends a right-button press/release pair and shows an armed hint | Make **tap, then tap-and-hold at the same spot** the primary gesture; retain the button only as an optional accessibility fallback and support a physical secondary button |
| Cursor | Android handles framebuffer/status events and ignores the existing IronRDP pointer output events | Render a visible cursor using existing pointer events, and provide accurate host position updates when the bundled server does not supply them |
| Drag | Left-down is deferred until a 4-point movement threshold and starts at the original touch position; leaving the image immediately cancels the gesture | Keep the original press location; capture the active gesture through movement outside the image and send one matching release |
| Phone keyboard | Focused typing field forwards committed text once; on-screen modifiers, navigation and F1–F12 exist | Preserve IME composition and keep essential keys reachable above the phone keyboard |
| Physical keyboard | Native navigation/modifier/F-key events have a release tracker, but are processed through the visible focused typing panel; letters and punctuation use text commits | Forward complete hardware press/release events while the remote view has focus, including when the phone keyboard is hidden |

Sources: [`android/src/remote_input.rs`](../android/src/remote_input.rs), [`keyboard.rs`](../android/src/keyboard.rs), [`lib.rs`](../android/src/lib.rs), shared [`Viewport`](../shared/src/lib.rs), and IronRDP [`RdpOutputEvent`](../vendor/ironrdp/crates/ironrdp-client/src/rdp.rs). Existing phone evidence is in [phone-test.md](phone-test.md); that evidence does not yet verify trackpad, cursor rendering or full hardware keyboard forwarding.

## Gesture rules and discoverability

- **Click:** direct touch uses the tap recognizer below. Moving beyond the drag threshold presses at the original contact location and moves with the finger. A stationary first contact sends no button while held; releasing it starts the buffered single-tap path. A standalone hold never right-clicks.
- **Scroll:** one-finger vertical/horizontal movement scrolls remote content. It never sends a click. Physical wheel events remain supported in Click, Scroll and Trackpad.
- **Pan:** one-finger movement changes the visible crop only. It never sends remote pointer input.
- **Trackpad:** one-finger movement changes a stored remote cursor by relative movement, without moving the cursor to the initial finger location. Stationary taps use the same single/double/right-click recognizer, targeting the stored cursor. Start with fixed movement sensitivity and reuse absolute RDP MOVE events to send the resulting RDP presentation-pixel position. A sensitivity setting can follow phone testing if needed.
- **Right-click:** tap, then touch the same screen spot again and hold to open the remote context menu. Show this hint beside Click and Trackpad and show hold progress at the contact. Keep **More → Right-click next tap** only as an optional accessibility fallback: it cancels buffered taps, then the next stationary completed tap sends one right pair without entering the double-tap recognizer. Movement/pinch cannot send left input or consume that armed action; **Cancel**, mode/view/target changes clear it. In Trackpad its optional button may right-click the cursor immediately.
- **Drag** in Trackpad explicitly holds the left button at the cursor. One-finger strokes move it, and lifting/repositioning the finger keeps it held so users can cross a large desktop. Show **Release drag** and a held-button indicator until released or cancelled. While this drag is held, contacts belong to dragging and cannot arm the tap/context recognizer; tapping Drag first clears pending clicks. Tap-then-hold is reserved for right-click.
- Two fingers exclusively control local pinch zoom in the first version, across all modes. Adding a second finger cancels a pending tap and releases any held remote button before zooming; suppress remote input until both contacts end. Continue using the explicit Scroll mode for touch scrolling, avoiding ambiguous two-finger scroll versus pinch classification.
- A physical mouse uses its own primary/secondary/middle press and release events; do not reinterpret every button as a touch tap. Show a short gesture hint for the selected mode. Controls must fit portrait width and remain available with the phone keyboard open.

### Buffered tap and hold recognition

Start with a **250 ms** interval from the first finger **up** to the second finger **down**, an **8-point** nearby radius in egui screen coordinates, and a **400 ms** stationary hold from second down. Movement slop starts at the existing **4 points**. Calibrate these values on the actual phone without changing the rules:

1. First down sends no button. Movement beyond slop starts an ordinary direct left drag, or relative Trackpad motion, and prevents tap recognition for that contact. A stationary release buffers the target and first tap until the inter-tap deadline.
2. With no qualifying second down by that deadline, send one left press/release pair. This deliberately delays single clicks by up to 250 ms, while local touch feedback is immediate. Sending the first click immediately would activate a remote target before the right-click gesture can be identified.
3. A second down within both interval and nearby radius keeps the first tap buffered. A stationary release before 400 ms emits two ordered left press/release pairs at the second contact's resolved remote target, or its stored cursor in Trackpad. A stationary hold reaching 400 ms discards the first tap and emits exactly one right press/release pair there, with no preceding left click. If the stationary second contact releases at or after 400 ms before a delayed timer repaint runs, emit that same single right-click on release. Record the committed action so timer and release cannot both emit it. Consume the contact until release so subsequent motion/lift sends no further click or drag.
4. Movement beyond slop during the second contact, before the hold commits, discards the buffered first tap and right-click candidate. It becomes an ordinary direct left drag starting at the second contact's remote origin, or ordinary relative Trackpad motion without a held button. No first-tap click leaks into that operation.
5. A second down outside the interval or radius commits the previous single tap and starts a new first contact. Multitouch, cancellation, mode/view/focus/target/geometry changes instead discard all buffered taps, release held input and suppress recognition until existing contacts end. Process cancellation/multitouch first, movement second and due timers last, so pinch or movement wins if received in the same frame as the hold deadline. Cancel/release before changing the viewport. Once a click pair has already committed it cannot be undone; later contacts must not emit an extra click.

Use the existing egui frame loop and `request_repaint_after` or equivalent for both deadlines, so a motionless hold fires. Store pending targets/deadlines with the current target and geometry generation; cancel them when either changes. Scope this recognizer to the remote desktop image; the terminal's standalone long-press remains local text selection. In terminal Interaction mode, delay app mouse-down until selection versus app input is resolved so selection cannot leak application mouse input.

## Coordinate mapping, cursor and zoom

1. Reuse the exact `image_rect` and UV crop calculated by `draw_stream` as the mapping contract. Letterboxed margins and toolbar taps cannot start remote input. Extend shared `Viewport` with the inverse mapping needed for RDP presentation-pixel cursor positions to appear at the same visible point used by touch mapping. Fit whole, Fill view, pinch and Pan must use the same transform.
2. Keep Trackpad cursor position in RDP presentation pixels and preserve it through finger lifts, local pan and zoom. Scale finger deltas using the displayed presentation span so a given finger movement has a consistent visible effect at the current zoom. Clamp to presentation bounds. Zoom must not change which remote point the cursor represents.
3. Coordinate with the [desktop targets plan](desktop-targets-plan.md): use its target generation and source/presentation geometry, including window origin, monitor scale and rotation. The host translates target coordinates to desktop coordinates once. Android must not add window/output offsets a second time. Reject stale frames/cursor updates and wait for matching geometry and the first current frame before enabling input.
4. Forward IronRDP `PointerDefault`, `PointerHidden`, `PointerPosition` and `PointerBitmap` from the existing receiver into cursor state. Cache the decoded bitmap/hotspot; paint it after the framebuffer and clip it to the displayed image. Respect hidden state, clear state at reconnect/target changes, and ensure software compositing and the overlay cannot draw two cursors.
5. Verify cursor information from both monitor capture and direct window capture before selecting the rendering path. If the bundled host sends no usable position, add a small authenticated cursor-state update to the existing control path while the live view is visible, using compositor position plus the selected target geometry. Pause it in Overview/Files/background. Use a default arrow when no shape is available; reuse RDP shape updates when present. A locally predicted cursor can respond immediately to sent input, then reconcile with host position. Label a purely local fallback as an input indicator; it does not prove the host cursor is at that position.
6. In Trackpad, keep the cursor within the visible crop by panning when it approaches the crop edge, including while dragging. Do not warp the remote pointer to achieve this. Direct touch and explicit Pan keep the user's chosen crop. Opening the keyboard shrinks the visible image and adjusts the crop to keep the active pointer visible; preserve zoom.

## Drag lifecycle and release guarantees

- Extend `RemoteInput` rather than creating a second gesture engine. Track the initiating contact, original remote press point, last sent point and held buttons. Finger/mouse motion outside the image continues an already active direct drag, clamped to its nearest presentation edge; it cannot start a fresh gesture or activate toolbar controls.
- Preserve event order: move to the press location, button down, ordered moves, final move, button up. Coalesce redundant motion only; never drop, reorder or coalesce button transitions. Calibrate the existing 4-point threshold on the phone for tap jitter and small text selections.
- Reuse `release_all` and keyboard `reset` through one app cleanup path on mode/view/target changes, geometry replacement, disconnect, pause, lost focus, system picker launch and touch cancellation. Pinch cancels dragging before viewport changes. Release at the last valid point using the old geometry before installing new geometry.
- Reserve room in the existing input queue for releases or report a failed send and end the session so host cleanup runs. If the transport is already closed, clear local state and rely on verified host session teardown to release held keys/buttons. Reconnect starts with no held input and never replays presses.
- Cursor following during a drag changes the local crop through the shared transform. Target resize or geometry replacement cancels the drag instead of silently moving its press point. A finger lift releases direct dragging; explicit Trackpad dragging releases only through **Release drag** or a lifecycle cancellation.

## Keyboard forwarding and visibility

- Keep the existing committed-text/IME deduplication and deletion logic for the phone keyboard. Preedit remains local. Reuse the special-key strip for both desktop and the new terminal, with each destination encoding its own RDP events or terminal bytes. Preserve the **Super** modifier label and the separate **Tap Super** action.
- Move hardware event handling out of `KeyboardControls::show` into the app event path. Route hardware input to the active remote view or terminal only while that destination has focus. Connection forms, menus and other local editors retain normal keyboard input.
- Expand the current scan-code mapping to letters, digits, punctuation, numpad, lock keys and left/right modifiers. Prefer physical key identity for shortcuts; choose and test the client/host layout policy explicitly. Capture Android key/device information at the existing NativeActivity boundary if egui events lose identity or cannot distinguish hardware text from IME commits.
- Send hardware key down, repeat and key up in order. Track exactly which remote keys are held and release them on focus/lifecycle changes. Prevent the same hardware printable key from also becoming an IME Unicode commit. Hardware modifiers remain held until their actual release; on-screen modifiers remain one-shot and must not release a hardware-held modifier when their shortcut finishes.
- Keep the phone keyboard optional when a Bluetooth/USB keyboard is attached. A visible **Keyboard** action and compact Esc/Tab/Ctrl/Alt/arrows strip remain accessible. Verify the existing visible-content bounds when the IME opens/closes or the phone rotates; the remote image and controls must stay above it.
- Android-reserved shortcuts may be intercepted before delivery. Identify actual device behavior during testing and keep the existing on-screen Super/function-key controls available for those combinations.

## Implementation order and acceptance gates

1. Implement buffered tap, tap-then-hold right-click and its progress hint; retain the optional accessibility fallback, centralize release cleanup and repair direct drag capture. Preserve Scroll/Pan/IME behavior and document single-click delay.
2. Add generation-aware cursor state and inverse viewport mapping, then Trackpad and explicit Drag/Release drag. Wire host cursor updates only if existing RDP events are insufficient.
3. Complete hardware forwarding using the existing scan-code helpers and release tracker; share only the reusable control UI with terminal input.
4. Record these checks on the actual paired Motorola phone, with a small host key/pointer recorder plus visible browser/editor targets. Use Bluetooth or USB hardware for hardware checks. Record results and screenshots in `phone-test.md`; unit checks supplement the phone evidence.

| Phone acceptance check | Passing result |
| --- | --- |
| Single tap, quick double tap and tap-then-hold on small browser/file targets in portrait and landscape, Click and Trackpad | One delayed left pair, two left pairs, or exactly one right pair respectively; right-click has no preceding left click and opens while held |
| Repeat at timing/radius boundaries; hold still, move before the hold deadline, add a second finger, cancel or switch modes | Stationary timer fires; movement becomes direct drag/relative motion; pinch/cancellation before commitment discards pending clicks; lift after right-click adds no click |
| Use the optional armed fallback, then drag, pinch, Cancel or switch modes | No unintended left/right click; armed state is explicit; Cancel/mode change clears it |
| Select multiline text, drag a scrollbar, and move/resize a desktop window in whole-monitor view | Press remains at the initial target, motion stays continuous, and release ends the operation |
| Drag to/beyond image edges, open controls, rotate, switch target, pause, launch a picker or lose the connection | No held button/key survives; reconnect has no ghost drag; every delivered press has a release or verified session cleanup |
| Use Trackpad to reach targets under the finger and across a zoomed desktop; lift/reposition during explicit drag | Cursor stays visible, does not jump on initial contact, follows the crop, and Release drag ends the operation |
| Move the host's physical mouse; change pointer shape and hide it over the remote target | Phone reconciles host position, renders the hotspot correctly, respects hiding and never draws two cursors |
| Repeat hit targets/cursor alignment at Fit whole, Fill view, 2×/4× zoom, after Pan and IME resize | Cursor and click refer to the same source pixel; margins do not send input; target moves/resizes do not reuse stale geometry |
| Hardware type punctuation/non-ASCII text and use Ctrl+C/L, Alt+Tab, Shift+arrows, Super, F1/F12, numpad and repeats | Expected remote keys/layout, no duplicate text, correct modifier lifetime, working with the phone keyboard hidden |
| Hold Ctrl/Shift/Alt or a navigation key while switching view, disconnecting or backgrounding | Recorder shows cleanup releases and the next session starts with no modifiers held |
| Phone IME composition, Backspace, Enter and multiline paste with controls visible | One commit per edit, composition stays local, controls remain reachable and image remains above the keyboard |

Keep scope inside the current Rust/egui/IronRDP input path and authenticated host control service. No separate input transport, gesture framework or imported remote-desktop application is needed.
